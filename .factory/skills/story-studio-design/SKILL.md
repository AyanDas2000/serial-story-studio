# Serial Story Studio design workflow

## Authority

This is a proposed project-local enforcement layer for Ayan's reset, not approval to build or spend. Later workers must explicitly read this file and its three references; discovery alone is not enforcement. Existing product docs are historical inputs. The current request and inspected source decide scope and capability claims.

Current priorities: actual model-backed writing, inspectable modular backend, a 30–40 episode psychological-thriller test, then a purposeful beautiful UI. USD 1 remains the application generation ceiling, including planning, drafts, revisions, extraction, critics and retries. Development Droid allowance is separate. Neither the target nor this skill permits calls. No automatic retry, fallback, model substitution, installation or release.

Read:
- `references/writer-loop.md`
- `references/motion-review.md`
- `references/evidence-gates.md`
- Current user instructions, source for affected capabilities, `docs/PRODUCT-DIRECTION.md` and `.stitch/DESIGN.md`. Do not turn documentation assertions into feature claims.

## Five requirements every later worker must obey

1. **Choose the surface before tokens.** Name the writer's task, current checkpoint, next decision and information hierarchy. Compare an existing-editor bridge with an editable writing desk. Explain the choice and get the applicable Ayan approval before implementing. The graph is an evidence lens, not the default writing workflow.
2. **Storyboard the entire loop and its states.** Direction → draft → feedback → revision → prose acceptance → memory confirmation → next episode. Include rejection, unsaved edits, stale basis, partial output, budget block, uncertain call and restart. Keep prose acceptance, memory confirmation and paid-call consent separate. Never represent a proposed gate as working backend behavior.
3. **Prove backend behavior and provenance before polishing.** Keep policy, context selection, provider boundary, persistence and UI distinct and inspectable. Explicitly label synthetic, pasted/manual, model-produced and human-edited model prose. A catalog listing, mocked response or `synthetic: false` flag alone does not establish a real model result.
4. **Specify only purposeful, interruptible motion.** Use the reference table with trigger, property, token, purpose, interruption and reduced-motion behavior. Do not animate typing, reading prose, recurring refreshes or every list just to satisfy a quota. A screenshot cannot verify motion.
5. **Deliver evidence and stop at Ayan's gate.** Cite source and actual test commands/results, attach pixels for visual claims and interaction recordings or observed runs for motion claims. Distinguish observed, inferred and unverified. No self-score substitutes for his judgment. No spending, deployment or progression through review gates without authority.

## Ordered workflow

### A. Capability and surface gate, before visual decisions

Write a short record:

```text
Writer outcome:
Backend capability / source location / observed or source-only:
Missing prerequisite:
Candidate surfaces and trade-off:
Chosen surface and why:
Current checkpoint / primary action / next checkpoint:
Primary information / supporting information / on-demand detail:
Out of scope:
Ayan decision required:
```

Default proposal, not approved layout: episode prose owns the main reading/editing area; relevant intention and continuity sit nearby; the current review task replaces the side workspace as the checkpoint changes. Source evidence stays one action away. Model routing and raw receipts are inspectable but do not compete with the manuscript. At narrow widths, preserve task order and source-return navigation, not a squeezed desktop grid.

Do not start with a font hunt, component registry, new accent or decorative signature. Existing tokens are an input after the surface decision. The existing Evidence Spine can become a useful passage → interpretation → next-context inspection path; do not add a static badge solely to pass a signature test.

### B. Storyboard and backend gate

Use `writer-loop.md` to produce state/action/authority/receipt rows. Bind approval to the exact saved revision and basis. Show backend prerequisites as blockers rather than simulated success.

For the thriller test, first define premise and evaluation cases with Ayan: unreliable narrator, death rumor, character-specific knowledge, delayed reveal, causal setup/payoff and revision propagation. Record expected interpretation before evaluating output. A model-backed 30–40 episode run remains a goal until access, cost feasibility and scoped calls are approved. Repeated fixture beats are not a thriller.

### C. Hierarchy, accessibility and tokens

Order decisions: task flow → information grouping → emphasis → density and reading measure → interaction states → type/spacing/color → motion.

Retain meaningful safeguards: accessible contrast on actual backgrounds, readable prose, visible keyboard focus, labels, touch targets, non-color meaning, long-text handling, reduced motion, safe text rendering and privacy. Keep one dominant action for the current task, not one filled button per unrelated form. Explain any local exception to stack rules for Ayan; do not silently change global skills.

No requirement to be more ornate. A sober familiar editor can be correct. Anti-slop scans are defect detectors, not a design generator. Do not introduce an unusual font or large heading simply to avoid a familiar look.

### D. Motion and review gate

Complete `motion-review.md` before animation code. Complete `evidence-gates.md` before reporting completion. If only source inspection is authorized, return hypotheses and a capture plan, not a visual verdict. If tools cannot provide evidence, state the blocker and hold the corresponding claim.

### E. Handoff

Return exact changed paths, source-backed capability changes, unresolved prerequisites, checks actually performed, and one next Ayan decision. Stop. Parent coordination, a successful test suite or a screenshot is not personal design approval.
